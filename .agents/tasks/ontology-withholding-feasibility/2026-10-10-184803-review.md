# TREC-CT MeSH fusion confirmation: implementation of protocol v7

The change adds the full confirmatory pipeline for the frozen protocol `protocol_trials_fusion.md` (v7). It has six parts: a shared library (`trials_domain/fusion_confirm.py`), six scripts under `scripts/trials_fusion_confirm/` (transfer check, fold builder, pins, training driver, scorer/gate 2, analysis), 37 unit tests, a remote runbook and a verification note. The estimator follows the protocol closely: validation-global z, per-variant nDCG@10 selection on {0..0.5} with the smaller-w tie rule, a group-aware derangement for the shuffled control, a two-level bootstrap with common random numbers, ordered Holm, and the 5-label rule. Both round-7 design items (gate-2 key-tuple leaf matching, anchored parser rows) are fixed in code and tested. No protected file was touched.

Watch for: the Mac smoke scored fusion on the fold-1 validation file. That puts 13 of the 52 "closed-unexposed" 2021 patients under fusion before the confirmatory run (confirmed). It also computed the new derangement C2 estimate on 15 of the 19 cohort-2022 checkpoints (confirmed). The verification note understates both, and the preregistered `unexposed_closed` premise no longer holds as written.

**Verdict**: NEEDS_CHANGES

## High-level view

The estimator matches the protocol. Weight selection and z-stats use only the validation file. `analyze.py` re-derives every w, aborts on any mismatch with `selected_w.json`, and reads test grades only after w is fixed. Per-patient metrics reuse `epf.rank_auc` and `epf.ranking_metrics`, so the undefined-patient set is the same for every score. c* and p* are drawn once per cohort and shared by every metric, variant and contrast. The C2/S4 states, Holm (ties → H1) and the 5-label rule match §1 and §4.3 exactly.

The CV design holds together. The fold builder reproduces the paraphrase components, the 23-topic exposure closure and the 5×15 folds. Paraphrase groups stay inside one fold. The trainer reads only `train.jsonl`, `validation_positive.jsonl` and the train/validation rows of `negative_pools.jsonl`, so no test-fold row reaches training. The shuffled control treats paraphrase components as groups, so no topic receives its own or a partner's MeSH set. This includes the cohort-2022 validation file, which holds the 26/63 pair.

Remote readiness is mostly in place. Scoring, gate 2, fold building and analysis assert `--device cpu` with no CUDA visible. Training refuses `CUDA_VISIBLE_DEVICES=""`. Pins probe the GPU in a child process. Every recorded path is repo-relative. The runbook excludes `/300`, `reports/` and `dev_local/`. The transfer check hashes all 18 inputs, the 15 checkpoints, the chunk digest and the MPNet revision. The code tree itself is shipped without any hash comparison, and the runbook still names an L40S rather than the user's A100.

The real gap is local exposure. To avoid confirmatory 2021 quantities, the dev smoke restricted the 2021 test side to already-exposed patients. It kept the inner-validation file whole, though, and that file is fold 1. Fold 1 is a confirmatory test fold, and 13 of its 15 topics are closed-unexposed. The deterministic zero-shot validation nDCG curves for all three φ variants were written to disk for those patients. The dev analysis also ran C2 with the new derangement on the 15 published 2022 checkpoints.

## Local exposure from the dev smoke

`score.py --dev-local` subsets the 2021 *test* records to `exposed_topics_closed`, but scores the inner-validation file whole. For outer fold 0, that file is fold 1: 2021_7, 9, 12, 14, 27, 29, 31, 32, 35, 43, 46, 47, 54, 64, 67. In the confirmatory CV, fold 1 is the test fold of k = 1. Of its 15 topics, 13 are outside `exposed_topics_closed` (all but 27 and 64).

`dev_local/scores/2021/fold_0/selected_w.json` holds the full validation nDCG@10 curve over w ∈ {0..0.5} for the hierarchy, exact and shuffled variants. Zero-shot is deterministic, so its curves are the exact values the confirmatory run will compute for those patients. The file shows fusion lowering zero-shot nDCG@10 on them, with w = 0.0 selected. The validation file caps grade 0 at 60, so it is not the test file. It still covers the same patients, the same grade-2 and grade-1 trials, and a subset of their grade-0 trials. That is directional outcome information about fusion on patients that §0 and §4.4 call "neither scored under fusion nor a paraphrase of a scored patient" (confirmed).

The verification note describes this as "one value … the deterministic zero-shot weight for outer fold 0 is w = 0.0". The real exposure is three full curves on 13 nominally unexposed patients, plus the 2-epoch smoke model's curves.

Cohort 2022 has a similar, smaller problem. The dev analysis ran the full C1–C3 and C2-state path on the 15 published checkpoints with the *new* group-aware derangement. The exploration had only seen a plain-permutation shuffle. These 15 checkpoints are 79% of the confirmatory C2_2022 input, and C2_2022 is the state that can force label 2. Cohort 2022 is already declared a frozen-pipeline confirmation, so this is a disclosure item, not a design flaw (confirmed).

Revision 1 does not exist yet, so the fix is cheap. Add a §9 entry with the 13 topics and the 2022 C2 preview. Then either shrink the preregistered subset to the 39 patients that remain unexposed, or keep 52 and add a 39-patient descriptive subset. Either way, the protocol edit happens before `verify_transfer.py` records its sha256. Any further smoke should subset the validation side too, or use a synthetic fold. The current code would repeat the exposure on whichever validation fold it touches (LOW, confirmed).

## Disclosed estimator deviations

Two small deviations are disclosed in the verification note and change no co-primary quantity. First, P@10 keeps `epf`'s 0 for a patient with no grade-2 trial, where §2.6 would treat the metric as undefined; this only adds Δ = 0 rows to S2. Second, `validation_positive.jsonl` follows the `validation.jsonl` order and is not reshuffled, because the protocol's file rule and its shuffle-seed list conflict.

For the round-7 MEDIUM, `leaf_class` checks skipped before exact, so `confusion_matrix` counts are never compared. That deviates from the review's literal order, and it is the right choice.

## Remote transfer and device policy

```
Mac ── rsync 1a (code tree, .git, .agents; excludes /results /preprocess /embedding_cache /300 /reports)
    ── rsync 1b (18 §7 inputs, 15×3 ckpt files, 2 prepared-cache dirs, preprocess/*.py)
    ── rsync 1c (MPNet snapshot)
                       │
remote: verify_transfer (hashes 1b + chunk digest + MPNet rev)   ← 1a is not hash-checked
        → pytest (gate 1) → build_cv2021 → cp -n cache → make_pins (records pins.code from remote files)
```

Every file whose hash is pinned in the protocol is checked. The code tree is not: `pins.code` records whatever arrived on the remote. A partial or stale rsync of an uncommitted study file would therefore be pinned as-is. Gates 1 and 2 would probably catch a broken file, but not a subtly stale one (LOW, confirmed). A Mac-side `code_hashes()` dump compared on arrival would close this.

The runbook says "the planned host is an L40S", but the user runs on an A100. The pinned `gpu_name` makes gate 3 GPU-agnostic, so only the text is wrong (NIT).

## Pins chain

`load_verified_pins` accepts a chain whose root is `dev_pins.json`. A `--revise` built on dev pins with a declared `confirmatory` change would yield a confirmatory-looking head inside `dev_local/`. This is contrived, because `make_pins` requires the output next to the previous revision. Still, the root check should require `pins.json` whenever the head is confirmatory (NIT, likely).

`analyze.py` records `score_manifest.pins` but never checks that it matches `--pins` (NIT).
